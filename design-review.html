iOS 26 product design review

Sevro

A strength-training utility for gym-goers to plan workouts, log sets and rest periods, and understand progress over time. The prototype has a credible, fast core loop, but it is not yet at Apple first-party quality because resilience, reachable information architecture, accessibility semantics, and native-system translation still have ship-blocking gaps.

01 / VERDICT

Promising core. Incomplete product.

What worksStarting and logging a workout is direct, with clear targets, immediate feedback, rest controls, and stable top-level navigation.
What blocks shipAn interrupted workout is lost; several product areas are unreachable; and critical accessibility and state coverage remain incomplete.
DecisionDo not translate screen-for-screen. Preserve the content model, then rebuild the shell and semantics with native SwiftUI components.
02 / SCORECARD

Apple-grade assessment

A3/5

Visual polish

Hierarchy is strong, but contrast failures, oversized editorial cards, bespoke effects, and non-SF iconography keep it from system-level restraint.

B3/5

Interaction & motion

Set logging feels responsive and Reduce Motion exists, but gesture-only editing, custom transitions, and an unsafe zero-set finish path remain.

C2/5

Architecture & flow

The four-tab model is coherent, yet unreachable profile and goal routes, seeded first-run data, and no completion summary make the product feel unfinished.

D3/5

Accessibility

Touch targets, modal focus, and reduced-motion paths are good; contrast, VoiceOver chatter, decorative announcements, and custom semantics are not.

E2/5

Platform integration

The prototype expresses app-like utility, but durable session state, native file flows, system containers, localization, and iOS surfaces are absent.

03 / PRIORITY

Top five if nothing else gets done

E1 · Persist every live-workout mutation

Reloading or termination currently erases the active session, elapsed time, completed sets, and rest state.

Critical

A1 · Replace failing custom colour pairs

Several 12–15 pt labels and destructive controls measure between 2.68:1 and 3.96:1, below 4.5:1.

High

B1 · Remove gesture-only editing

Tracked bests, per-muscle targets, and builder reordering depend on long press or drag without a complete visible alternative.

High

C1 · Make profile, goals, and progress routes reachable

Implemented screens and editors exist in code but have no path from the rendered Settings or Insights hierarchy.

High

D1 · Stop announcing the rest timer every second

The live region updates continuously and can monopolise VoiceOver while the user is trying to log or edit the next set.

04 / INVENTORY

What exists

Inventory is based on rendered routes, state branches, overlay builders, and event bindings in prototype/app.js. “Unreachable” means the code exists but no rendered control links to it.

Screens and routes

  • HomeDefault “Today’s workout” and active-session Resume state; weekly volume and strength cards.
  • WorkoutsBrowse, edit mode, active split, collapsed/expanded history, start and detail actions.
  • Workout detailExercise summary, Start workout, Edit workout.
  • Workout builderNew/edit, empty/populated, disabled save, counters, remove and reorder.
  • Split builderWeekday/numbered modes, assignment selectors, active split editing.
  • Live workoutExercise/Overview modes; planned, next, logged, missed, skipped, resting, exercise-complete and finish states.
  • InsightsDefault strength/volume/bests state and active-workout exercise progress state.
  • SettingsAppearance, accent, units, rest timers, export and restore.
  • ProfileImplemented but unreachable.
  • GoalsImplemented but unreachable.
  • Personal BestsImplemented but unreachable as a dedicated route.
  • Exercise progressImplemented but reachable only through the unreachable Personal Bests route.

Reusable components and overlays

  • ShellCustom app frame, top headers, bottom tab bar, back header.
  • Cards and rowsContent cards, list rows, workout cards, metric/stat cards, set rows, overview cards.
  • ControlsPrimary/secondary/ghost buttons, segmented controls, chips, steppers, counters, custom switch, colour swatches.
  • FeedbackStatus live region, press animation, set confirmation, haptic abstraction, rest countdown, progress bars.
  • ChartsStrength line chart/scrubber, volume bars, goal progress, circular strength score.
  • SheetsStandard splits, split preview, exercise picker, previous session, live add exercise, set editor, swap, profile editor, goal type/target, volume help, restore.
  • DialogsFinish workout and delete workout.

State coverage

Default / populated

Strong coverage across all primary screens.

Active / completed workout

Active, resting, skipped, missed, complete, partial finish and discard states exist.

Disabled

Builder saves, picker Done, and movement controls expose disabled states.

Long content

375 × 812 pt and simulated accessibility text showed no horizontal overflow.

Dark / light

Both themes and system-following choice exist; Reduce Motion, Contrast and Transparency CSS paths exist.

First run

No honest new-user state; seeded history and goals appear immediately.

Empty collections

No workouts/history/goals empty experiences; exercise search can become blank.

Loading

No loading or importing state for restore, export, sync, or initial data hydration.

Error / recovery

No file, persistence, validation, sync, or import failure UI with retry.

Offline / stale / conflict

No model for restored data, cloud conflicts, stale summaries, or sync status.

No permission

Not currently applicable; must be added if notifications, HealthKit, or Live Activities request access.

Localization / RTL

Only English, hard-coded dates and direction-specific gestures are represented.

A · Visual polish — 3/5
A1
Custom colours fail text contrast
prototype/styles.css · .focus-workout span, .editorial-copy small, .insight-score strong, .insight-change, .set-row.missed .set-copy span, .secondary.danger

What’s wrong. Measured source pairs include 3.39:1, 3.64:1, 3.63:1, 3.40:1, 3.27:1 and 2.68:1 respectively on their light surfaces; the affected labels are 12–15 pt, so they miss 4.5:1.

Recommended change. Replace fixed decorative colours with semantic roles; target ≥4.5:1 in both appearances and ≥7:1 where practical. Darken light-mode green/blue/red labels and verify every custom accent against its actual surface.

SwiftUI note. Use Color.primary, .secondary, .tint, and asset-catalog variants for custom roles; test Increase Contrast. Source: HIG Accessibility.

HighEffort S
A2
Dynamic Type is simulated, not modelled
prototype/styles.css · :root --type-*, html[data-text-size="large"], html[data-text-size="accessibility"]

What’s wrong. The prototype collapses iOS typography into default, large, and one accessibility bucket using fixed rem tokens. Runtime at 375 × 812 showed no horizontal overflow, which is good, but it does not prove every category through accessibility5 or Bold Text.

Recommended change. Map each role to an Apple text style, allow multiline labels, and switch dense horizontal groups to vertical layouts from accessibility1 upward.

TRANSLATION RISK. Do not port the rem table. Use .font(.body), .headline, .title2, @ScaledMetric, and test DynamicTypeSize.accessibility5. Source: DynamicTypeSize.

HighEffort M
A3
Surface styling is too bespoke for a utility
prototype/styles.css · .screen, .home-editorial-card, .insight-hero, .workout-select-card, .bottom-nav, .sheet

What’s wrong. Multiple radial gradients, translucent card layers, 22–29 px radii, colour-mixed shadows, and custom blurred bars compete for attention. The hierarchy reads, but the total treatment feels designed-on rather than system-owned.

Recommended change. Keep one content-card radius (16–20 pt), one low elevation, opaque grouped backgrounds under Reduce Transparency, and reserve material for navigation/presentation chrome.

TRANSLATION RISK. Use native bars and system materials; do not reproduce CSS backdrop filters or the custom “glass” stack. Source: Liquid Glass.

MediumEffort M
A4
Icon language mixes custom SVG and text glyphs
prototype/app.js · icon(), mainNav(), settings(), workouts(), insights(); selectors .glyph, .chev, .ios-link.plus

What’s wrong. The interface mixes hand-drawn SVG, “＋”, “›”, “⌁”, “♕”, “◷”, and arrow text. Stroke weight and optical centring vary by component.

Recommended change. Define an explicit symbol map and use consistent hierarchical rendering, scale, and weight.

TRANSLATION RISK. Replace with Image(systemName:) such as house, dumbbell, chart.xyaxis.line, gearshape, plus, chevron.right, timer, and crown. Source: HIG SF Symbols.

MediumEffort S
A5
Home summary cards are over-tall
prototype/styles.css · .home-editorial-card; Home · “Your week”

What’s wrong. Each weekly summary card is at least 208 px and measured 246 px at compact runtime, placing roughly 500 px of secondary information ahead of anything below.

Recommended change. Reduce these to compact 140–168 pt cards or a horizontally paged pair only if paging is discoverable; keep the workout card dominant.

SwiftUI note. Use adaptive Grid or ViewThatFits, not fixed heights; allow the copy to determine height at large text.

PolishEffort S
B · Interaction and motion — 3/5
B1
Important editing remains gesture-only
prototype/app.js · bind() [data-toggle-bests], [data-volume-longpress]; builderRows() .builder-drag-handle

What’s wrong. Personal-best tracking enters edit mode only after a 500 ms hold; per-muscle targets appear only after long press; builder reordering has hold/drag and keyboard arrows but no visible touch alternative.

Recommended change. Add visible Edit actions, explicit move up/down actions, and keep context menus or drag as accelerators.

SwiftUI note. Use EditButton/List.onMove, visible Buttons, and accessibility actions. A contextMenu may supplement, never replace, the visible route. Source: HIG Accessibility.

HighEffort M
B2
Navigation motion is CSS-authored
prototype/styles.css · .transition-forward, .transition-back, .transition-tab, .transition-exercise-*; .sheet

What’s wrong. Whole-screen translate/fade animations and a custom sheet rise duplicate system navigation and presentation behavior. Reduce Motion is respected, but causality and interactive dismissal would be lost in a literal port.

Recommended change. Keep custom motion only for set confirmation and exercise-to-exercise continuity; let navigation, tabs, alerts, and sheets use system transitions.

TRANSLATION RISK. Use NavigationStack, TabView, .sheet, and confirmationDialog; gate remaining animation with accessibilityReduceMotion.

MediumEffort M
B3
Finish can silently discard a zero-set workout
prototype/app.js · finishFlowSets(), cancelWorkout(); Live workout · Finish

What’s wrong. If no set has an outcome, tapping Finish calls cancelWorkout() immediately. There is no confirmation, undo, or explanation, even though elapsed time and any in-session edits are lost.

Recommended change. Always present a confirmation: “End workout?” with Keep Working and Discard Workout; use destructive styling and preserve the draft until the choice resolves.

SwiftUI note. Use confirmationDialog with Button(role: .destructive); restore focus to Finish on cancellation. Source: HIG Buttons.

HighEffort S
B4
Web vibration is not a native haptic contract
prototype/app.js · haptic(), logSet(), startRest(), saveSession()

What’s wrong. The prototype encodes haptics as millisecond vibration arrays. Those patterns do not map directly to iPhone haptic semantics and risk becoming noisy if copied conceptually.

Recommended change. Define events, not waveforms: set logged, rest almost complete, rest complete, skipped, workout completed. Use success/selection/impact sparingly.

TRANSLATION RISK. Map events to .sensoryFeedback(.selection), .impact, or .success; respect system haptic settings.

MediumEffort S
C · Information architecture and flow — 2/5
C1
Implemented product areas are unreachable
prototype/app.js · profile(), goals(), bests(), progressPage(), editProfileSheet(); settings() and insights()

What’s wrong. Profile, goal management, the dedicated bests list, exercise drill-down, and profile editing exist in code, but Settings and Insights render no controls that reach them. [data-edit-profile] is bound but never rendered.

Recommended change. Put Profile, Goals, and Data under Settings; make Personal Bests rows navigate to exercise progress; delete dead routes if they are not shipping.

SwiftUI note. Model destinations as typed NavigationStack values and add navigation tests for every route.

HighEffort M
C2
Workout completion has no summary
prototype/app.js · saveSession(); transition from Live workout to Insights

What’s wrong. Saving clears the live session, switches tabs to Insights, and emits only “Workout saved.” The user never sees duration, volume, completed sets, PRs, skipped sets, or a clear Done action.

Recommended change. Present a completion summary before returning to the app: session totals, PRs, notable progress, Share, and Done.

SwiftUI note. Present a focused summary with NavigationStack or fullScreenCover; use ShareLink for an optional result card.

HighEffort M
C3
First launch presents fabricated history
prototype/app.js · state.workouts, state.sessions, state.goals; home(), workouts(), insights()

What’s wrong. A new state is seeded with seven completed sessions, goals, PRs, and a 4.9% strength gain. In production this would misrepresent user data and hide the true first-run experience.

Recommended change. Start with a short setup: units, experience, optional template; then show honest empty states with one next action. Keep sample data only in preview/demo builds.

SwiftUI note. Gate setup with persisted onboarding state; use ContentUnavailableView for empty Home, Workouts, and Insights.

HighEffort M
C4
Collection and search empty states are absent
prototype/app.js · workouts(), goals(), renderExercisePicker(); .picker-results

What’s wrong. Deleting all workouts or having no history/goals leaves blank sections. Runtime search for “zzzz” produced an empty sheet with filters and no message or recovery.

Recommended change. Add scoped empty states: Create a Workout, Start Your First Session, Set a Goal, and “No exercises match” with Clear Filters.

SwiftUI note. Use ContentUnavailableView.search(text:) for no results and tailored ContentUnavailableView variants for empty collections.

MediumEffort S
C5
Loading, error, offline, and conflict states are unmodelled
prototype/app.js · state, localStorage reads/writes, data-export, data-restore-confirm; all data-backed screens

What’s wrong. Persistence failures are swallowed, restore is a placeholder, and no screen can show importing, retry, stale data, sync conflict, or partial recovery.

Recommended change. Define a shared load state and explicit recovery copy for initial load, save failure, corrupt backup, offline restored data, and sync conflict. Never clear the current dataset until an import validates.

SwiftUI note. Use an observable store with explicit idle/loading/loaded/failed state and task cancellation; surface retry inline instead of generic alerts.

HighEffort L
D · Accessibility — 3/5
D1
Rest countdown creates VoiceOver chatter
prototype/app.js · liveScreen() .rest-countdown[aria-live="polite"], syncRestAction()

What’s wrong. The polite live region changes every second. Runtime exposed both the countdown and status toast live regions, so ongoing announcements can interrupt navigation and mask higher-value feedback.

Recommended change. Keep the visual timer silent; announce only “Rest started, 90 seconds,” “10 seconds remaining,” and “Rest complete.” Expose the current value when the timer receives focus.

SwiftUI note. Use a non-live Text(timerInterval:), accessibilityValue, and narrowly timed AccessibilityNotification.Announcement.

HighEffort S
D2
Decorative glyphs enter the accessibility tree
prototype/app.js · settings() .glyph, workouts() .pr-badge/.chev, profile()/bests(); runtime Settings

What’s wrong. Runtime accessibility output included “☾”, “⌁”, “↑”, “↓”, and “›” in otherwise labelled rows. These add noise and can cause Voice Control ambiguity.

Recommended change. Hide decoration; combine each icon, title, metadata, and state into one coherent row element. Keep meaningful values in labels or values, not symbol names.

SwiftUI note. Apply .accessibilityHidden(true) to decorative Images and use .accessibilityElement(children: .combine) selectively.

HighEffort S
D3
The strength chart is exposed as a Slider
prototype/app.js · insights() [data-chart-scrub][role="slider"], bindChartScrub()

What’s wrong. The chart is a time-series exploration surface but is announced as one scalar Slider. That hides the time dimension and implies the user is changing a value rather than inspecting data.

Recommended change. Provide a concise trend summary and expose individual data points or an adjustable chart selection with date and value.

TRANSLATION RISK. Use Swift Charts with an accessible chart descriptor and chartXSelection; do not translate the HTML slider role literally.

MediumEffort M
D4
System controls are visually imitated
prototype/app.js · settings() .choice-control, [data-rest-toggle] .switch; liveScreen() .segmented; createSplit() .split-mode-control

What’s wrong. Theme, units, rest timers, live modes, and split modes use button groups or a decorative switch. ARIA is mostly present, but native focus, value announcements, Button Shapes, and On/Off Labels would have to be recreated.

Recommended change. Preserve labels and grouping but replace each imitation with its semantic control.

TRANSLATION RISK. Use Picker(.segmented), Toggle, and TabView; add concise accessibilityLabel/Value only where defaults are insufficient.

MediumEffort M
E · Platform integration — 2/5
E1
Active workouts are not durable
prototype/app.js · state.live/state.elapsed/state.rest, startWorkout(), logSet(), adjustActiveRest(), saveSession()

What’s wrong. Live session state exists only in memory. A reload or process termination removes the workout, set outcomes, edits, elapsed time, and rest timer; only workout templates and preferences are persisted.

Recommended change. Persist the active session after every mutation, store absolute timestamps rather than decrement-only counters, recover on launch, and offer Resume or Discard.

SwiftUI note. Use SwiftData/Core Data for local-first durability, observe scenePhase, and derive elapsed/rest time from saved dates. Add migration and corruption recovery tests.

CriticalEffort L
E2
Backup and restore are placeholders
prototype/app.js · settings() [data-export]/[data-restore], bind() export toast, [data-restore-confirm]

What’s wrong. Export only reports a toast; restore ends with “File picker would open on iPhone.” There is no file validation, preview, progress, failure, cancellation, or success detail.

Recommended change. Define a versioned document format, preview counts/date before replacement, validate before mutation, and keep a rollback snapshot.

SwiftUI note. Use FileDocument, fileExporter, fileImporter, and ShareLink; handle security-scoped URLs and malformed data.

HighEffort L
E3
Locale and layout direction are hard-coded
prototype/index.html · html[lang="en"]; prototype/app.js · seeded date strings, string-built units and plurals; prototype/styles.css · left/right positioning

What’s wrong. Dates such as “Monday, 14 Sep,” unit strings, “1 exercises,” left/right positioning, and directional transitions are authored directly. No RTL state exists.

Recommended change. Define the launch locale set, localize all strings and plurals, format dates/measurements, and use leading/trailing layout semantics.

SwiftUI note. Use String Catalogs, plural inflection, Date.FormatStyle, Measurement, and LayoutDirection; test an RTL locale. Source: HIG Layout.

06 / ADDITIONS

Ranked by impact ÷ effort

These are additions beyond the current prototype. Ranking favours changes that reduce workout interruption and decision friction before broader ecosystem features.

01

Live rest status outside the app

Problem. People lock the phone or switch apps between sets and can miss rest completion. Location. Lock Screen, Dynamic Island, and optional local notification.

SwiftUI approach. ActivityKit Live Activity backed by absolute rest-end time; local notification fallback; actions to Skip or +15 s through App Intents.
MHigh impact
02

First-run workout setup

Problem. An empty new account needs a fast path to a credible first workout without fabricated history. Location. First launch, then Settings → Training setup.

SwiftUI approach. Short NavigationStack flow for units, experience, days, and template; skip is always available; end in an honest ContentUnavailableView.
MHigh impact
03

Completion summary and share card

Problem. Finishing lacks closure and makes PRs hard to notice. Location. Immediately after Save.

SwiftUI approach. Summary screen with duration, volume, PRs, skipped sets, recovery note, Done, and optional ShareLink using a rendered privacy-safe card.
MHigh impact
04

Resume and start App Intents

Problem. Starting the common workout or returning to an interrupted session requires opening and navigating the app. Location. Shortcuts, Siri, Spotlight, Action button, Control Center.

SwiftUI approach. AppIntent for Start Workout and Resume Workout with AppEntity workout selection and deep links.
MMedium-high impact
05

Next-workout and weekly-progress widgets

Problem. Users need the next action and weekly status without entering the app. Location. Home Screen and Lock Screen widgets.

SwiftUI approach. WidgetKit timeline from the shared durable store; small widget starts/resumes, medium widget adds weekly progress.
MMedium impact
06

iCloud sync with explicit conflict handling

Problem. Workout plans and history should survive device replacement and work across iPhone/iPad. Location. Invisible by default; status and recovery under Settings → Data.

SwiftUI approach. SwiftData/Core Data with CloudKit, local-first writes, deterministic merge rules, last-sync status, and an export escape hatch.
LHigh impact
07

Actionable training reminders

Problem. Planned training days and unfinished sessions are easy to forget. Location. Settings → Notifications and notification actions.

SwiftUI approach. UserNotifications with granular opt-in, scheduled-day reminders, Resume action, and no engagement spam.
MMedium impact
08

Spotlight exercise and workout search

Problem. Larger libraries make in-app browsing slower. Location. System Spotlight and deep-linked results.

SwiftUI approach. Index workouts and exercises with Core Spotlight; deep link into workout detail or exercise progress.
SLower impact

Deliberately not recommending

  • Social feed or leaderboards: adds moderation, comparison pressure, and product sprawl without improving the logging loop.
  • AI-generated coaching: introduces safety and trust risk before the underlying training data and completion states are reliable.
  • Apple Watch logging in the first release: high interaction and sync complexity; validate the durable iPhone flow first.
  • HealthKit strength prescriptions: the data model and user benefit are not yet specific enough to justify permissions and privacy cost.
  • Competitive streaks: can encourage training through poor recovery; weekly consistency and goals already cover the useful signal.

Ship-blockers

  • A1 contrast corrections and semantic colour assets
  • B1 visible alternatives for every long press and drag

Later
